# Runtime import audit — Phase 4

Assessment: **2026-10-20 · v0.0.4-runtime-audit**. Baseline SDK: ReXGlue 0.10.0, commit `f5337cdc947ff6d4c4196737e2c807a48f2a1fc2`.

**VERIFIED:** all **261 imported functions** have been mapped to a pinned source body, raw hook or stub macro and assigned a source-audit classification. Counts: **7 IMPLEMENTED, 184 PARTIAL, 61 STUB, 9 UNKNOWN**. These are static implementation assessments, not 261 runtime conformance tests. The 13 imported variables are outside the requested function count; their loader mappings were recorded in Phase 2.

- **IMPLEMENTED:** substantive behavior at the inspected shim boundary, including the described result/error handling, with no identified missing action for that limited contract. This does not establish every input case or Horizon compatibility.
- **PARTIAL:** meaningful behavior exists, with known approximation, incomplete paths or unvalidated required subsystem/platform behavior. Delegation to a kernel object is not full compatibility proof.
- **STUB:** warning-only/no-op, fixed refusal, fabricated result or success without the named operation. A stub is not automatically an exercised boot blocker.
- **UNKNOWN:** wrapper found, but underlying behavior/ABI/conformance was not sufficiently established. The eight formatting/logging hooks and SHA helper are explicitly retained here.

The matrix gives each function's library/ordinal, classification, reason, observed status constants and exact source location. Status constants are tokens present directly in each body, not a list of every possible transitive failure. No runtime implementation, game patch, key material or proprietary code was added.

## Initialization and early execution priorities

**VERIFIED static evidence:** a conservative graph of direct emitted `callee(ctx, base)` calls starts at the generated `xstart` entry mapped to `0x827F1498`. Its closure contains 141 symbol nodes, including **33 imported functions**: 2 IMPLEMENTED, 28 PARTIAL, 2 STUB, 1 UNKNOWN. This is an over-approximation of direct source call paths and an under-approximation of dynamic calls; it is not an execution trace, branch-feasibility proof or complete boot call graph.

Prioritize allocation/protection, TLS, critical sections/events/waits, module/header lookup, XConfig and error/termination paths appearing in that closure. The two reachable stub candidates are `XamShowMessageBoxUIEx` and `XGetAVPack`; neither is proven fatal at boot. The unknown is `DbgPrint`'s formatter. Establish deterministic diagnostic behavior before using it as the only source of a boot failure report. P0/P1/P2 below express engineering order, not proof a function runs.

### Exceptions

**VERIFIED:** `RtlRaiseException` has three direct callers in emitted output and a static path from `xstart` through CRT-related routines. This makes exception behavior a credible early failure-path dependency (**INFERRED**), not a proof exceptions are normally thrown during initialization (**UNKNOWN**). It handles a debugger thread-name exception, examines the C++ exception case and ultimately breaks into debugging; general unwinding is explicitly TODO. [Exception dispatch](https://github.com/rexglue/rexglue-sdk/blob/f5337cdc947ff6d4c4196737e2c807a48f2a1fc2/src/kernel/xboxkrnl/xboxkrnl_debug.cpp#L129).

`RtlCaptureContext` has two emitted direct callers and `RtlUnwind` three; neither appears in the limited entry closure. `__C_specific_handler` has no literal direct call in this scan, which says nothing about table-driven handler dispatch. Phase 3 identified 106 functions sharing registers with SEH funclets; the game's active exception paths and complete handler requirements remain UNKNOWN. [Warning-only implementations](https://github.com/rexglue/rexglue-sdk/blob/f5337cdc947ff6d4c4196737e2c807a48f2a1fc2/src/kernel/xboxkrnl/xboxkrnl_rtl.cpp#L557).

**BLOCKED for exception-capable execution:** context capture, stack unwind and handler results are not produced. Returning normally can skip cleanup or continue with invalid context; actual corruption was not observed because the game was not run. General code compatibility will be needed if those paths execute; do not invent replacement behavior or assume they are unused. First separate optional debugger naming from C++/SEH throw, rethrow, cleanup and termination requirements using narrowly scoped private traces or static call-site examination.

### STFS and I/O manager

**VERIFIED:** `StfsCreateDevice` returns `X_STATUS_SUCCESS` without creating a device; the `out_device` write is commented out. `StfsControlDevice` returns success without applying its ioctl or filling outputs. Success therefore does **not** establish initialized output or a completed operation. [Exact shims](https://github.com/rexglue/rexglue-sdk/blob/f5337cdc947ff6d4c4196737e2c807a48f2a1fc2/src/kernel/xboxkrnl/xboxkrnl_io.cpp#L749).

**INFERRED risk:** consumers that trust success can use stale/uninitialized output, skip fallback or falsely accept content state. This is not a safe general failure contract; no actual corruption or required boot call was measured. The generic stub macro is similarly nondeterministic: it logs and leaves PPC `r3`/outputs unchanged, so `r3` may still contain the first argument. [Macro behavior](https://github.com/rexglue/rexglue-sdk/blob/f5337cdc947ff6d4c4196737e2c807a48f2a1fc2/include/rex/hook.h#L51).

No literal direct call to either STFS import appears in the prior emitted function bodies. **UNKNOWN:** use through pointers, export lookup, callbacks, omitted modules or later content/DLC paths, and whether boot needs STFS at all. The SDK has a separate host-side STFS container parser/content path; that is not an implementation of these guest I/O-manager APIs. [Container device](https://github.com/rexglue/rexglue-sdk/blob/f5337cdc947ff6d4c4196737e2c807a48f2a1fc2/src/filesystem/devices/stfs_container_device.cpp).

Do not implement STFS speculatively. Establish which content root/device APIs execute with the existing extracted base, then validate explicit failure/output handling and only the required operations. User-visible save/DLC success must never be inferred from these constant-success shims.

### Other concrete risks

`XamAlloc` reports success even if its heap allocation returns zero. `XamTaskSchedule` writes a fixed task handle; task close/exit polling are stubs. Session APIs fabricate `0xCAFEDEAD` / `0xDEADF00D`. Signature verification/signing stubs return success without doing cryptography. Vd system command identifiers are fabricated, scaler output is NOPs, and several no-GPU paths only warn. These are source-confirmed behaviors, not claims every path is used. They require observation-driven handling, not broad replacement of all 61 stubs.

`RtlCompareMemoryUlong` increments its result once per matching 32-bit word and returns that count. For a fully matching eight-byte input it therefore returns 2 rather than 8. This conflicts with Microsoft's [documented Windows byte-count contract](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-rtlcomparememoryulong); the exact Xbox contract and effect at its static early call sites remain UNKNOWN. Its source also flags an unresolved endian assumption. Do not classify this routine as implemented from its nonempty body.

`RtlCompareStringN` computes expanded sentinel lengths but then uses the original length arguments for the comparison bound. This is a concrete edge-case concern; no speculative change was applied. Error paths using host assertions/debug breaks are not equivalent to recoverable Xbox status returns.

## Recommended order and feasibility

1. Keep the VMX findings visible and obtain independently justified Xbox conversion/special-value evidence before changing the SDK; fix/propose alias-safe emission only with isolated regressions.
2. Establish guest memory/TLS/module state, deterministic diagnostics and selected early synchronization contracts using original probes. Repair sleep-inclusive/calendar supervision before any future analyzer run.
3. Audit the static early exception path and distinguish debugger naming from actual unwind/handler requirements. Do not treat a host exception adapter as a guest exception solution.
4. Observe base-file/content access and justify any required STFS behavior. Validate outputs/failures before save/content experiments.
5. Only then consider a bounded private entry trace, followed separately by graphics/audio/input and Horizon probes. No full game build or Switch deployment is authorized by these findings.

**Verdict: PARTIAL.** The Phase 3 mechanical analysis/generation pass stands, but runtime-correct execution is BLOCKED pending VMX special-value evidence and required memory/exception/API contracts. Boot necessity of individual stubs remains UNKNOWN. [VMX tests and results](vmx128-validation.md) · [Feasibility](../feasibility.md) · [Roadmap](../roadmap.md).
